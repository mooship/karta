# `@karta/theme`

A typed, compile-time-checked view onto Karta's Material 3 design tokens, built with [vanilla-extract](https://vanilla-extract.style/)'s `createGlobalThemeContract`. Has no dependency on any other Karta package, Leaflet, or React.

## What belongs here

- **`vars`** — the M3 colour, shape, elevation, state, and motion roles documented in `docs/design-system.md` (`vars.color.primary`, `vars.shape.cornerMedium`, `vars.elevation.shadow2`, `vars.state.hover`, `vars.motion.easeStandard`, …).
- **`mapLabelVars`** — the app-specific composite map-label tokens layered on top of the M3 roles (`mapLabelVars.surface`, `.surfaceSecondary`, `.outline`, `.text`).

Both are built with `createGlobalThemeContract`, which declares **no values and emits no CSS**. A host app (`packages/web`'s `src/index.css`, generated by `scripts/generateM3Theme.ts`) stays the single source of truth for every token's actual value and for light/dark switching — this package exists purely so a `.css.ts` file can write `vars.color.primary` instead of hand-typing `"var(--md-sys-color-primary)"`, where a typo fails silently rather than at compile time.

Every field is **fallback-free**: unlike `@karta/map`'s own bespoke typography/spacing/control-sizing contract (`packages/map/src/theme/mapTokens.ts`), these are treated as an unconditional dependency with no sensible generic default for a missing colour role.

```ts
// Button.css.ts
import { vars } from "@karta/theme";
import { style } from "@vanilla-extract/css";

export const button = style({
  background: vars.color.surfaceContainer,
  borderRadius: vars.shape.cornerMedium,
  boxShadow: vars.elevation.shadow1,
});
```

## Integration requirement

Because this package (and any consumer's own `.css.ts` files) ship source with no build step, a host app must register `@vanilla-extract/vite-plugin`'s `vanillaExtractPlugin()` in its own Vite config, and must itself define every custom property `vars`/`mapLabelVars` resolves to — see `packages/map/README.md`'s "Styling" section and `docs/design-system.md`'s "Styling implementation" section for the full requirements and a reference implementation.

## What doesn't belong here

- Actual token values, or light/dark switching logic — those live in whichever host app defines the underlying CSS custom properties.
- `@karta/map`'s own bespoke tokens (fonts, spacing, control sizing, z-index, mobile layout) — those have documented fallbacks and live in `packages/map/src/theme/mapTokens.ts` instead, since a missing M3 colour role has no sensible generic default but a missing `@karta/map` component-sizing token does.
