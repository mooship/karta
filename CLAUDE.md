# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository — the codebase's architecture and conventions below — plus operating rules, under "Delegating to sub-agents" and "Dynamic workflows", for how Claude itself should delegate and orchestrate work while doing so.

## About

Karta is a reusable SDK for building public-interest geospatial layer platforms: a domain-agnostic layer model, generic map rendering, React hooks, and a typed design-token contract (`@karta/core`, `@karta/map`, `@karta/react`, `@karta/theme`) that any dataset can be wired into. `packages/app` and `packages/web` are the SDK's reference implementation, not the product — a real, published SSR app on Cloudflare Workers (no accounts, no tracking beyond cookieless page views) that proves the SDK out end-to-end. That implementation's one domain, `spatial-apartheid-legacy`, maps apartheid-era spatial planning legacy across South African metros using one combined regional map layer: recognized township areas, formal transit routes, modeled car drive-time to selected job centers, and a combined spatial-burden score weighting the two together. That domain's data currently covers two regions: `gauteng` (all nine Gauteng municipalities, including Tshwane/Pretoria and Johannesburg) and `western-cape` (City of Cape Town) — both regions' pipeline output is generated and published under `packages/web/public/data/`.

## Commands

```bash
npm install
npm run test           # vitest across the npm workspaces under packages/*, plus data-pipeline (see vitest.config.ts projects)
npm run test:coverage  # vitest run --coverage, same scope; thresholds are 95% statements/branches/functions/lines (vitest.config.ts), enforced in CI but not pre-commit
npm run typecheck      # tsc --noEmit for @karta/core, @karta/app, @karta/theme, @karta/map, @karta/react + web build + data-pipeline typecheck
npm run build          # build all workspaces
npm run lint           # biome check . && npm run depcruise — dependency-cruiser, enforcing the SDK package dependency direction below (see .dependency-cruiser.cjs)
npm run format         # biome format --write .
npm run dev --workspace @karta/web
```

Run a single test file: `npx vitest run path/to/file.test.ts` (or `npx vitest path/to/file.test.ts` to watch).

CI (`.github/workflows/ci.yml`) runs, in order: a Paraglide freshness check (`npm run messages:compile --workspace @karta/web` then `git diff --exit-code -- packages/web/src/paraglide` — fails if compiled output wasn't committed after editing `messages/{en,af}.json`, see the `packages/web` entry below), `npm run lint`, `npm run typecheck`, `npm run test:coverage`, `npm run validate --prefix data-pipeline` (re-validates the committed pipeline output against its manifest/checksums, without re-running the pipeline), then `npm run build`. Lighthouse (`.github/workflows/lighthouse.yml`) and Playwright (`.github/workflows/playwright.yml`) run as separate workflows on every PR.

Playwright end-to-end tests live in `packages/web/e2e/`. They are not part of `npm run test`; CI runs `npm run test:e2e:all --workspace @karta/web` (both projects below) in the dedicated `playwright.yml` workflow:

```bash
npm run playwright:install --workspace @karta/web   # once, downloads Chromium (used by both projects below)
npm run test:e2e --workspace @karta/web              # runs both the "chromium" and "mobile-chromium" (Pixel 7) projects
npm run test:e2e:local --workspace @karta/web        # chromium project only
npm run test:e2e:mobile --workspace @karta/web       # mobile-chromium project only
npm run test:e2e:ui --workspace @karta/web           # Playwright's interactive UI runner
```

`playwright.config.ts`'s `webServer` auto-runs `npm run build && npm run preview:e2e -- --port 4173` and waits on `localhost:4173` — no separate build/serve step needed. `preview:e2e` is `wrangler dev` against `wrangler.e2e.jsonc`, a copy of the root `wrangler.jsonc` with the `routes`/custom-domain block removed, so the e2e run never exercises `workers/app.ts`'s old-hostname redirect (see the `packages/web` entry below). Basemap tile requests are mocked to a 1x1 PNG in the suite, so it doesn't depend on OSM/Esri availability.

`data-pipeline/` is **not** an npm workspace — it's a standalone project with its own `package-lock.json`, but its vitest suite is still included as a project in the root `vitest.config.ts`, so `npm run test` and CI's `test` step run it too:

```bash
cd data-pipeline
npm install
npm run run                        # full pipeline: fetch boundaries/transit, OSRM routing, join, validate, atomically publish to packages/web/public/data/<regionId>/
npm run run -- --region gauteng    # a single region instead of every province-kind region in REGIONS
npm run validate                   # re-validate already-published region output against its manifest/checksums, without re-running the pipeline
npm run display                    # legacy helper: rebuilds compact display files for per-metro source directories when present
npm run cache:prune                # remove OSRM/Overpass response-cache entries older than 7 days (also takes --max-age-days N)
npm run cache:clean                # remove the whole data-pipeline/.cache directory
```

The pipeline calls public third-party APIs by default (`router.project-osrm.org` for drive-time; an Overpass mirror rotation for transit — see `data-pipeline/README.md`'s "Rate limits" section). `OSRM_BASE_URL`/`OVERPASS_URL`/`OVERPASS_URLS` (read only by `src/constants/serviceUrls.ts`) point the pipeline at self-hosted instances instead (`data-pipeline/docker-compose.yml`) for heavy iteration without those rate limits. `PIPELINE_CACHE=0` disables the local response cache; `PIPELINE_CACHE_DIR` relocates it.

Pre-commit (lefthook) runs biome (auto-fix staged files), dependency-cruiser (`npm run depcruise`), and the full vitest suite — expect all three to run on every commit. It does **not** run typecheck, the Paraglide freshness check, or coverage thresholds; those are CI-only, so a commit passing pre-commit can still fail CI.

## Safety

- **Never deploy `packages/web` to Cloudflare Workers production without explicit permission from the user.** Always ask first and wait for confirmation.
- **Never run the full data pipeline (`npm run run` in `data-pipeline/`) or publish its output to `packages/web/public/data/` without asking first.** It calls third-party rate-limited APIs (OSRM, Overpass) and overwrites committed region data. `npm run validate` (re-checks already-published output against its manifest, no network calls) is always safe to run unprompted.

## Architecture

**Three parts, one direction of data flow:** `data-pipeline` (offline, run manually) → static GeoJSON committed per-region under `packages/web/public/data/<regionId>/` → `packages/web` (client-side fetch for map data; there is no runtime API route for map data itself). `packages/web/src/routes.ts` defines six routes total: `home.tsx` (the map) and `privacy.tsx` are the only two with UI; `robots.txt.ts`, `sitemap.xml.ts`, and `llms.txt.ts` are resource routes (no default export) whose `loader`s return static text built once at module scope from `constants/siteConfig.ts`'s `SITE_URL` and (for `llms.txt.ts`) `layers/registry.ts`'s `getLayers()`/`getStory()` — none of them touch map data or vary per request. `routes/log-error.ts` is the only route with a real per-request `action`, logging client-side error reports server-side; see the `packages/web` entry below. `packages/app` is the contract both ends agree on, built on top of the domain-agnostic model in `packages/core`.

- **packages/core** — domain-agnostic layer model (`Layer`, `LayerGroup`, `DomainStory`, style config types, in `types/layer.ts`), a Leaflet config factory (`createLayerConfig`, converting a `Layer` into Leaflet `pathOptions`/`styleFn`), a registry factory (`createRegistry`, exposing `getLayers`/`getLayer`/`getLayerGroups`/`getStory` over a `DomainConfig`), and geodata utils (`fetchFeatureCollection`, `mergeFeatureCollections`, and the Zod schemas in `geoJsonSchemas.ts` — whose coordinate interiors are checked by plain predicates wrapped in `z.custom` rather than nested `z.array(z.number())` schemas, identical checks but ~10x faster at GeoJSON's scale, where a single published layer carries tens of thousands of positions — `featureCollectionSchema`, `polygonGeometrySchema`, `multiPolygonGeometrySchema`, `createFeatureCollectionParser`). `src/spatial/` adds Turf/proj4-backed geodata primitives with no Leaflet or domain dependency: `nearestFeatureDistance` (straight-line km from a point to the nearest of a set of Point/LineString geometries, falling back to nearest-point-on-line for routes), `isPointInPolygon` (point-in-polygon over a `Polygon`/`MultiPolygon` or a `Feature` wrapping one), `unionBoundingBoxes`/`featureCollectionBounds` (bbox union and extent, both `[minLng, minLat, maxLng, maxLat]`), and `reprojectPosition`/`reprojectGeometry`/`reprojectFeatureCollection` (proj4-backed reprojection of an arbitrary source CRS into WGS84, GeoJSON's RFC 7946-mandated CRS — `reprojectGeometry` walks coordinates via Turf's `coordEach` against a single proj4 `Converter` built once per call, rather than a hand-written per-geometry-type recursive case or reconstructing the converter per coordinate). `DomainConfig`'s `story` field (`{ title, body }`) is optional — a domain with nothing to say there simply omits it, and `getStory()` returns `undefined`. Every export is JSDoc-documented. Has no dependency on `packages/app`, `packages/web`, or React — it's the first package extracted towards a reusable SDK.

- **packages/app** (`@karta/app`) — domain-specific constants (metros, regions, townships, transit layer ids), domain data, and domain-specific GeoJSON type definitions, spanning Gauteng and Western Cape. `types/genericLayer.ts` still re-exports the `Layer`/`LayerGroup` contracts (style config, geometry kind, interaction, grouping/selection mode) from `@karta/core`, which any domain's layers must satisfy, but `domains/spatial-apartheid-legacy/layers.ts` imports `Layer` directly from `@karta/core` rather than through that stub. `domains/spatial-apartheid-legacy/` (`layers.ts`, `layerGroups.ts`, `index.ts` exporting `SPATIAL_APARTHEID_LEGACY_DOMAIN`) is the first concrete domain built on those types — it wires up the layer catalogue (three township-area choropleths sharing one `commuteMinutes`/`nearestTransitKm`/`spatialBurdenScore`-keyed dataset, plus one line layer per transit network), layer groups, and a `story` (`{ title: "Why this map exists", body }`), now a proper `DomainConfig` field rather than an ad hoc extra one (the `rapid-rail` and `commuter-rail` layers set `hasPointGeometry: true`, since real station/stop Point geometry only exists for those two networks). `layers.ts`'s `dataUrl()` builds a single Gauteng-only URL (for `rapid-rail`/`bus`, which have no Western Cape equivalent source configured); `multiRegionDataUrls()` builds one URL per given region (for `bus-rapid-transit`/`commuter-rail`, whose pipeline configs both regions define a source for) — `packages/app` can't import `buildRegionDataUrls()` from `packages/web`, so this is a small local equivalent. `constants/regions.ts` defines `REGIONS` (`gauteng` and `western-cape`, both kind `province`), the registry driving per-region output directories and data-fetch URLs. `constants/metros.ts` defines `METROS` (the nine Gauteng municipalities plus City of Cape Town), each tagged with a `regionId`, used by the pipeline while building a region's dataset. `constants/townships.ts` defines included township-area groupings per metro. `types/` also holds domain-specific GeoJSON/transit contracts. Renamed from `packages/shared`/`@karta/shared`. `domains/heritage-sites/` (`HERITAGE_SITES_LAYERS`, `HERITAGE_SITES_LAYER_GROUPS`, `HERITAGE_SITES_DOMAIN`) is a second, national-scope domain — a single hand-authored Point layer of publicly documented anti-apartheid and democracy heritage sites, with no `data-pipeline` source behind it — that exists purely to prove `DomainConfig`/`Layer` carry no region or metro assumption; it is deliberately not wired into `packages/web`, which still publishes only `spatial-apartheid-legacy`.

- **packages/map** — generic map rendering components (`MapView`, `Legend`, `DesktopLegend`, `MobileLegend`, `LocationSearchControl`, `FeatureBrowser`, UI primitives `IconButton`/`SegmentedControl`/`ControlButton`/`ThemeToggle`/`BasemapToggle`/`SettingsMenu`), a `DomainProvider` React context plus `useDomain()` hook wrapping `createRegistry` from `@karta/core`, `resolveTileScaleToken` (which resolves Leaflet's `{r}` tile-scale placeholder from the caller's retina decision, since Leaflet otherwise resolves it from the device pixel ratio alone and serves `@2x` tiles even where `detectRetina` is off), and Leaflet-specific utilities (`constants/basemaps.ts`, `constants/mapStyles.ts`, `data/locationSearch.ts`). `DomainProvider` must wrap any component tree that calls `useDomain()` — directly (`Legend`, `MapView`, `FeatureBrowser`) or transitively (`DesktopLegend`, `MobileLegend`); `useDomain()` throws if called outside one. `MapView` takes a domain-agnostic `bounds` prop (no baked-in Gauteng bounds), a `renderFeaturePopup` callback so popup content stays caller-defined rather than hardcoded to a Gauteng township shape, and an optional `onLayerDataError` callback fired with the ids of overlay layers whose data failed to fetch (from its internal `useLayerData` call), so a failed background fetch isn't silently invisible to the caller, and an optional `onReady` callback fired one animation frame after Leaflet's `whenReady`, so a caller can hold its own bulk `areas` data back until the map is actually on screen. It imports `react-dom/server`'s `renderToStaticMarkup` dynamically, on first popup bind, so React's server renderer isn't in the vendor chunk every visitor downloads before the map paints (`vite.config.ts`'s `react-vendor` code-splitting group deliberately excludes it; giving it a *named* group instead makes React Router emit a `modulepreload` and fetch it up front anyway). `usePrefersDarkMode`/`useThemePreference` are imported directly from `@karta/react` (no re-export stub). Built on `@karta/core` and `@karta/react`; still has no dependency on `packages/app` or `packages/web`, taking `DomainConfig`/`Layer` values as props/context instead. `LocationSearchControl`'s `handleResultSelect` sets a `justSelectedRef` flag before calling `setQuery(result.label)`, and its debounced search `useEffect` checks and clears that flag before doing anything else — `setQuery(result.label)` is itself a `query` change, which would otherwise re-trigger the same debounced search after `SEARCH_DEBOUNCE_MS` and reopen the dropdown with the just-picked result a moment after selection. `LocationSearchControl` takes an optional `provider` (a `GeocoderProvider`, `{ search, reverse }`), defaulting to `data/locationSearch.ts`'s `nominatimGeocoderProvider`; `createNominatimGeocoderProvider({ countryCodes })` builds one biased toward a host's own coverage area (`fetchLocationSearchResults`/`fetchReverseGeocodeResult` are the underlying OpenStreetMap Nominatim calls) — a host wiring up any provider is responsible for allowlisting its origin in its own CSP `connect-src`, since the SDK has no runtime hook into that. `MapView`'s optional `locationContextMenu` prop (via `LocationContextMenu`) offers reverse-geocoding a right-clicked/long-pressed point through that same provider. `MapView` also owns an internal measuring tool — `MeasurementControl` (the floating panel UI, purely presentational) and `MeasurementLayer` (the click-to-add-point preview line/polygon on the map) — surfaced via `measurementTool`/`measurementPanelOpen`/`onMeasurementPanelClose` props, backed by `@karta/core`'s `measureLineDistance`/area functions in `spatial/measurement.ts`; `FeatureBrowser` is a separate, domain-agnostic component (not part of `MapView`) that lists every selectable feature `MapView` reports via `onSelectableFeaturesChange`, grouped and ordered by the active domain's layers via `useDomain()`, filterable by label — a caller wires its `onSelect` to its own selected-feature state, which `MapView`'s `SelectedFeatureHighlight` turns into a fly-to-and-open-popup. `constants/basemaps.ts` is an extensible, module-level basemap registry (`registerBasemap`, `getBasemapDefinition`, `getRegisteredBasemapIds`, `resetBasemapRegistry`, `getBasemapTileSources`) seeded with `positron` (the default), `liberty`, and `dark` (all `"vector"`-kind, OpenFreeMap-served) plus `satellite`/`topo` (Esri raster basemaps); it also accepts further `"vector"`-kind `BasemapDefinition`s (a MapLibre GL style JSON URL, plus optional light/dark `attribution` since a style JSON's own `sources` don't necessarily carry one), rendered by `VectorBasemapLayer` via `maplibre-gl`/`@maplibre/maplibre-gl-leaflet`, lazy-loaded via dynamic `import()` on first selection since most sessions (on a raster basemap) never need MapLibre's ~270KB gzipped payload — `positron` is the one built-in basemap that pays this cost on every session, since it's also the default; any consumer can `registerBasemap` a further raster or vector one. None of the five built-ins auto-swaps style with the app's light/dark UI theme (`darkStyleUrl`/`dimInDarkMode` stay unset on all of them) — a basemap's own style and the UI chrome's theme preference are treated as unrelated choices, `dark` is just another basemap a user picks directly, and `topo`/`satellite` are left to render as-is under a dark UI rather than being CSS-inverted. The `positron`/`liberty`/`dark` OpenFreeMap styles replaced this app's former CARTO-served `street`/`voyager` basemaps after CARTO's previously-used free anonymous basemap tile endpoints (`basemaps.cartocdn.com`) started returning HTTP 200 with a baked-in "API KEY REQUIRED" watermark image instead of actual tiles or an error — see `packages/map/src/constants/basemaps.ts`'s own comment for the detail, `packages/map/src/constants/basemapHealth.test.ts` for a live-network regression check against a repeat (a CARTO-style silent watermark swap specifically isn't catchable this way — see that file's own comment), and `packages/web/public/_headers`' CSP (`worker-src 'self' blob:`, `tiles.openfreemap.org` in `img-src`/`connect-src`) for what a host embedding a vector basemap needs to allow. Every component is styled with vanilla-extract (`*.css.ts`, colocated beside each component), reaching the M3 design tokens through `@karta/theme`'s `vars`/`mapLabelVars` and this package's own bespoke typography/spacing/control-sizing/z-index/mobile-layout contract through `theme/mapTokens.ts`'s fallback-preserving `designTokens`/`zIndexTokens`/`mobileLayoutTokens` helpers (wrapping the existing `DESIGN_TOKEN_CSS_VAR_DEFAULTS`/`Z_INDEX_CSS_VAR_DEFAULTS`/`MOBILE_LAYOUT_CSS_VAR_DEFAULTS` constants in `var(name, default)` so a `.css.ts` file can't reference one and forget its fallback); built on `@karta/core`, `@karta/react`, and `@karta/theme`.

- **packages/theme** (`@karta/theme`) — a small, dependency-free package holding a typed, compile-time-checked view onto the M3 design tokens documented in `docs/design-system.md`: `vars` (colour/shape/elevation/state/motion) and `mapLabelVars` (the app-specific composite map-label tokens), both built with vanilla-extract's `createGlobalThemeContract`, which declares no values and emits no CSS — a host app (`packages/web`'s `index.css`, generated by `scripts/generateM3Theme.ts`) stays the single source of truth for every token's actual value and for light/dark switching; this package exists purely so a `.css.ts` file can write `vars.color.primary` instead of hand-typing a `var(--md-sys-color-primary)` string, where a typo fails silently rather than at compile time. Unlike `@karta/map`'s own bespoke token helpers, every field here is fallback-free: these are treated as an unconditional dependency with no sensible generic default. The fourth package extracted towards a reusable SDK.

- **packages/react** — generic React hooks with no map/domain dependency: `usePrefersDarkMode()` (tracks the OS `prefers-color-scheme: dark` media query), `useResolvedDarkTheme()` (combines `useThemePreference()` and `usePrefersDarkMode()` into the single boolean a caller actually renders against — the OS preference only when the stored preference is `"system"`), `useThemePreference()`/`setThemePreference()`/`initTheme(config)` (a `useSyncExternalStore`-backed theme preference store, persisted to `localStorage`, syncing `document.documentElement.dataset.theme` and a `<meta name="theme-color">` override), `useModelContextTool(definition)`/`isModelContextSupported()` (registers a [WebMCP](https://webmachinelearning.github.io/webmcp/) tool via `document.modelContext.registerTool()`, so an in-browser AI agent can discover and call it, and unregisters it via `AbortController` on unmount or when `definition` becomes `null`), `useCanHover()` (media-query check for a hover-capable primary pointer, initialising `false` to avoid an SSR mismatch, for gating hover-only affordances that would otherwise misfire from a touchscreen's synthetic mouse events), `useIsDesktopViewport()`/`MOBILE_BREAKPOINT_PX`/`getViewportWidth()` (the shared desktop/mobile layout breakpoint), and `useLatestRef(value)` (keeps a ref assigned during render, not in an effect, so an event listener bound once by outside code reads the current value instead of closing over a stale one). `initTheme({ storageKey, colors })` must be called once at app bootstrap, before hydration, with app-specific values — the theme storage key/colour pair isn't baked into the hook; calling `initTheme` also re-reads the already-stored preference under the new key, since the module's own top-level read (at import time, before `initTheme` can run) used the built-in default config. `useModelContextTool` re-registers only when `definition`'s `name` changes identity (including transitions to/from `null`) — `description`/`inputSchema` are captured once at registration time, since every current caller's schema is static for a given tool name, and a fresh `execute` closure on every render (the common case, since it closes over current component state) is read via a ref instead, so it can't itself trigger register/unregister churn; it's a no-op wherever `document.modelContext` is unsupported or denied by Permissions-Policy. The third package extracted towards a reusable SDK.

- **data-pipeline** — pipelines are described declaratively as a `RegionPipelineConfig` (`src/pipelineSource.ts`): a `regionId`, the `metros` it covers, and a list of `PipelineSource` entries (`layerId`, `fetch()`, `outputFileName`) each responsible for producing one transit layer's `FeatureCollection`. `src/regions/gautengPipelineConfig.ts` wires up Gautrain rail/bus, PRASA rail, A Re Yeng, Rea Vaya, Ekurhuleni IRPTN, and Tshwane bus fetchers into `GAUTENG_PIPELINE_CONFIG`; `src/regions/westernCapePipelineConfig.ts` wires up MyCiTi (a new adapter, `src/adapters/myciti.ts`, mirroring `reaVaya.ts`'s route-relation pattern) and PRASA rail — reusing `adapters/prasa.ts`'s existing fetcher as-is rather than a new adapter, since its Overpass query already matches on operator/network regardless of region — into `WESTERN_CAPE_PIPELINE_CONFIG`. Both configs share one `createFetchWithPublishedFallback(regionId)` factory (`src/fetchWithPublishedFallback.ts`) for their fetch-with-fallback-to-last-published-output behaviour, extracted out of `gautengPipelineConfig.ts` once a second region needed the identical logic. `src/run.ts` runs `runRegion(config)` (looped across every configured region by `runAllProvinceRegions()`, or invoked for a single region via `npm run run -- --region <id>`): loops through the config's `metros` to fetch boundaries and per-metro OSRM job-center routing, runs each `PipelineSource.fetch()`, computes nearest-transit distance and a combined `spatialBurdenScore` (`src/spatialBurden.ts`, 60/40 commute/transit weighted, fixed-scale normalized), then writes that region's combined dataset under `packages/web/public/data/<regionId>/` (including `townships`, `township-areas`, and one file per configured transit source, plus `.display.v1.geojson` variants). `src/transitDistance.ts`'s `computeNearestTransitKm` and `src/constants/metroBbox.ts`'s `getSharedTransitBbox` now delegate their actual distance/bbox-union math to `@karta/core`'s `nearestFeatureDistance`/`unionBoundingBoxes` rather than hand-rolling it, keeping only the Overpass-string bbox parsing/formatting and the per-network fallback-to-published-data logic local.

- **packages/web** — `layers/registry.ts` wraps `createRegistry` from `@karta/core` around `SPATIAL_APARTHEID_LEGACY_DOMAIN`; there is no metro argument or per-domain selector yet since only one domain is published. `@karta/app` stays the single source of truth for domain *structure* (ids, data sources, styling, availability) in English; `layers/registry.ts`'s getters apply `layerTranslations.ts`'s `localizeLayer`/`localizeLayerGroup`/`localizeStory` to that structure's output at call time, overlaying *display text* (label/description, choropleth `style.buckets[].label`, a line/point layer's `style.legendLabel` mirroring its translated `label`, layer group title/description, and the domain story) from the current locale's `messages/{locale}.json` — keyed by layer/group id, falling back to the English original for any id without a translation entry so a new `@karta/app` layer still renders rather than breaking. `colorClassification`/`radiusClassification` stop labels (e.g. "Rea Vaya") are deliberately left untouched: those are transit operators' actual brand names, not descriptive copy. Every getter must resolve this fresh per call rather than caching a translated value at module scope — Cloudflare Workers reuse isolates across requests, so a module-scope value would freeze in whichever locale first touched that isolate instead of reflecting each request's own; `registry.ts`'s own `createRegistry(SPATIAL_APARTHEID_LEGACY_DOMAIN)` stays module-scope-safe precisely because it holds only that locale-independent structure. The re-export stubs that used to sit between web and the SDK packages have been removed: `App.tsx` and its components import `createLayerConfig`, `fetchFeatureCollection`, `mergeFeatureCollections`, `MapView`, `Legend`, `DesktopLegend`, `MobileLegend`, `LocationSearchControl`, the shared UI primitives, `getBasemapTileSources`, `usePrefersDarkMode`, and `useThemePreference`/`initTheme` directly from `@karta/core`, `@karta/map`, and `@karta/react`; `useLayerData` similarly lives only in `@karta/map`, not in web. `data/geoJsonSchemas.ts` re-exports the generic schemas from `@karta/core` and adds the township-specific `townshipFeatureCollectionSchema`. `constants/themeConfig.ts` holds the app-specific `THEME_COLOR`/`THEME_STORAGE_KEY` values (the `buffer-zones-theme` storage key predates the Karta rename and is kept as-is to avoid discarding users' stored preference); `entry.client.tsx` calls `initTheme({ storageKey: THEME_STORAGE_KEY, colors: THEME_COLOR })` before `hydrateRoot`, and `root.tsx` pulls the font, Leaflet and app stylesheets in as plain side-effect imports (not `?url` + explicit `<link rel=stylesheet>`), so the bundler emits fewer render-blocking stylesheets and React Router's `<Links>` emits them itself — they must stay module imports rather than CSS `@import`s, since inlining them that way happens before `FontaineTransform` can add its metric-matched fallback `@font-face` rules, which is what keeps CLS at 0 while the web fonts swap in; `links()` emits no `<link rel=preload>` for layer GeoJSON at all, default-visible or not, because nothing can consume it until the map bundle has hydrated and mounted Leaflet, so preloading only starves the render-critical requests of bandwidth. `Layout` inlines a `THEME_BOOTSTRAP_SCRIPT` (importing `THEME_STORAGE_KEY` directly, since it's a route module rather than a static file) as a `<script>` to set `data-theme` pre-hydration and avoid a flash of the wrong theme — inlined rather than an external `/theme-bootstrap.js` file so it doesn't cost a separate render-blocking request; its exact source is hashed into `public/_headers`' `Content-Security-Policy` `script-src`, so changing that string means recomputing the `sha256-` hash there too. `App.tsx` wraps its whole render tree in `<DomainProvider domain={domain}>`, where `domain` is `{ layers: getLayers(), layerGroups: getLayerGroups(), story: getStory() }` built from `layers/registry.ts`'s own (localized) getters rather than importing `SPATIAL_APARTHEID_LEGACY_DOMAIN` from `@karta/app` directly — the same localized data both feeds `LayerToggles`/the Story tab and reaches `@karta/map`'s `Legend`/`MapView` (via `useDomain()`), so a layer's legend entry and its entry in the layer-toggle list always show the same translated text. `domain` is computed inside `App`'s render body via `useMemo(..., [])`, not at module scope, for the same per-request-locale reason as `layers/registry.ts`'s getters (both `MapView` and the always/conditionally-rendered `DesktopLegend`/`MobileLegend` need `useDomain()`), passes `MapView` a `bounds` prop of `SEARCH_COVERAGE_BOUNDS` (mainland South Africa's extent — see below — reused directly rather than a second hand-synced constant, so the map opens framing the whole country rather than just whichever regions have published data) and a `renderFeaturePopup` that renders `TownshipPopup`, which stays web-local since popup content is domain-specific. Each transit-overlay layer's `dataSource` is built in `layers.ts` (`packages/app`) by one of two local helpers, since `packages/app` can't import web's `buildRegionDataUrls()`: `dataUrl()` (a single Gauteng-only URL, for `rapid-rail`/`bus`, which have no Western Cape source configured) or `multiRegionDataUrls()` (one URL per given region, for `bus-rapid-transit`/`commuter-rail`, whose pipeline configs both regions define a source for). Only the choropleth township/area fetch in `App.tsx` calls `buildRegionDataUrls()` directly — bypassing `Layer.dataSource` entirely — to merge every configured region's `townships`/`township-areas` files into one `FeatureCollection`. Both that fetch and `@karta/map`'s `useLayerData` use `Promise.allSettled` (not `Promise.all`) across a merge's region/source URLs and render whatever succeeded, rather than one region's fetch failure (e.g. its data not published yet) blanking out another region's already-working data — `App.tsx`'s own merge only shows the retry-banner error state once every region's *township* data (not just `township-areas`, a companion display layer with no properties of its own) has failed. UI state in `stores/useMapUiStore.ts` contains layer visibility, basemap, panel state, and selection only; there is no metro or region selector state. `App.tsx` fetches every region's township/area data and merges the resulting `FeatureCollection`s client-side, but only once `MapView`'s `onReady` callback fires (`mapReady` state) — that data is hundreds of kilobytes and seconds of parse/render work on a mid-range phone, and starting it at mount put all of it in front of the map's own first paint — that data feeds the map's choropleth layers, `TownshipPopup` (rendered via `renderFeaturePopup` on every map feature click, unconditionally), and — via `MapView`'s `onSelectableFeaturesChange` — the Browse tab's `FeatureBrowser`; `MapView`'s internal `useLayerData` call does the same per-layer for transit overlays, reporting failures back to `App.tsx` via an `onLayerDataError` callback that `LayerToggles` surfaces as a per-layer badge; `LayerToggles` also renders each `Layer`'s own optional `description` beneath its label (`aria-describedby`-linked to its checkbox, whose accessible name is pinned to the label text alone via `aria-labelledby` so the description doesn't get folded into it). The info panel shows `LayerToggles` by default, plus up to two further tabs (an ARIA `tablist`/`tabpanel`, `panelViews`/`panelLabels` computed inside `App`'s render body, `panelView` state in `useMapUiStore`): a "Story" tab rendering the domain-local `DomainStory` component from `App`'s own `story` (`domain.story`, itself `getStory()` from `layers/registry.ts`), shown only when the active domain defines a `story`; and a "Browse" tab rendering `@karta/map`'s `FeatureBrowser` over every selectable feature `MapView` reports, shown only when the active domain declares at least one `interaction.selectable` layer. A domain with neither gets today's single-view panel with no tablist at all — this replaces an earlier, web-local `TownshipBrowser`/`AskAiPanel` pair (and their `DATA_SOURCES`/`REPOSITORY_URL` constants, and the `EvidenceSummary` methodology copy that was never domain-config-driven) that was removed and later superseded by `FeatureBrowser`, which is domain-agnostic and lives in `@karta/map` rather than web-local. `useMapPermalink` restores `visibleLayerIds`/`basemap`/`panelView`/`selectedFeatureId` from the URL's query string on load (dropping any unknown layer id, unregistered basemap, or unrecognised panel view rather than applying it, since a shared link can outlive a domain's current layer catalogue) and keeps the URL in sync afterwards, so the address bar is always a shareable link to the current view; it defers applying a shared `selectedFeatureId` until `townships` has data, since Leaflet has nothing to select before then. `App.tsx` passes `!isDesktopViewport && panelOpen` to `MapView` as `measurementPanelOpen`, and `closePanel` as `onMeasurementPanelClose`, so `MapView`'s own measuring tool (see the `packages/map` entry above) collapses to its idle toggle rather than competing with the mobile info-panel sheet for the same sliver of screen. `panelViewport` (`App.css.ts`) carries `paddingInline` because `overflow-y: auto` implicitly makes `overflow-x` clip too, which was cutting off full-width children's `:focus-visible`/`:hover` effects at the edges. `App.tsx` has no runtime API route to call, and there are no Cloudflare bindings to thread into route modules — `workers/app.ts`'s `fetch(request)` first 301-redirects the old `buffer-zones.timothybrits.co.za` hostname (still live as a second `routes` entry in `wrangler.jsonc`) to `SITE_URL`'s current host, then passes everything else to the React Router request handler with no `RouterContextProvider`, wrapped in a `try`/`catch` that logs via `console.error` and returns a 500 for a failure outside the render lifecycle entirely (the render/loader/action path is already covered by `entry.server.tsx`'s `onError` and `root.tsx`'s `ErrorBoundary`, both of which also log via `console.error`) — together with Cloudflare's own Workers Logs (`observability.logs`/`traces` in `wrangler.jsonc`), this is the app's full server-side error logging. `paraglideMiddleware` is deliberately **not** called in `workers/app.ts` — it's wrapped inside `entry.server.tsx`'s `handleRequest` instead (see below), because `workers/app.ts` is bundled straight from source by wrangler/esbuild while `entry.server.tsx` is bundled by Vite as part of `react-router build`'s server output; those are two separate bundlers producing two separate copies of `paraglide/runtime.js`, each with its own module-scope `AsyncLocalStorage`. Wrapping in `workers/app.ts` would populate only its own copy's storage — `root.tsx`'s `getLocale()` call (built into the Vite-bundled copy) would never see it and would silently fall back to `baseLocale` ("en") regardless of the request's locale cookie or `Accept-Language`, a mismatch client-side hydration then papers over after the fact rather than before first paint. The one gap that leaves — a client-side JS exception that never touches a render or the server — is closed by `clientErrorReporting.ts`'s `installClientErrorReporting()`, called once from `entry.client.tsx` before hydration: it listens for uncaught script errors and unhandled promise rejections and reports each via `navigator.sendBeacon` (falling back to `fetch` with `keepalive: true`) to `routes/log-error.ts`, a resource route whose `action` validates the report (bounding every string field via `CLIENT_ERROR_REPORT_MAX_FIELD_LENGTH` in `constants/clientErrorReporting.ts`) and logs it, storing nothing server-side — see `PRIVACY.md`'s "Error reporting" section. `LocationSearchControl` is passed `locationSearchProvider`, this app's own `@karta/map` `createNominatimGeocoderProvider({ countryCodes: "za" })` — biased toward South Africa, unlike `@karta/map`'s unbiased default `nominatimGeocoderProvider`, since a domain-agnostic SDK component can't assume any host's coverage area. `App.tsx`'s `handleLocationSelect` checks the picked result against `SEARCH_COVERAGE_BOUNDS` (`isWithinSearchCoverage`, a plain numeric rectangle-containment check) before flying the map to it — Nominatim searches the whole world, so a result outside South Africa shows an inline "outside South Africa" message (`outOfCoverageLocationLabel` state, `outOfCoverage` in `App.css.ts`) instead of silently panning to an empty basemap. `MapView`'s `bounds` prop is `SEARCH_COVERAGE_BOUNDS` itself (mainland South Africa's extent) rather than a rectangle tighter around just the published regions — the basemap and search stay usable across the whole country even where nothing is mapped, e.g. Durban, and the map opens framing that same whole-country extent rather than zooming straight in on whichever regions happen to have data. `App.tsx` also calls `hooks/useMapModelContextTools.ts`'s `useMapModelContextTools`, which registers this app's capabilities as WebMCP tools (via `@karta/react`'s `useModelContextTool`) so an in-browser AI agent can list/toggle layers, search a location, switch the basemap/theme, and read the domain's story: `list-map-layers`, `toggle-map-layer`, `search-map-location`, `set-map-basemap`, `set-app-theme`, and — only when `getStory()` returns a `story` — `read-map-story`. Layer, basemap, and theme tools read/write `useMapUiStore`/the layer registry/`setThemePreference` directly, since those are already stable, globally reachable APIs; the search and story tools instead take `onLocationSelect`/`onShowStory` as options, since they close over `App`'s own local component state (the search focus target, the panel's open/view state) that isn't in the shared store. `App.tsx`'s `handleLocationSelect` is the single function passed both to `LocationSearchControl`'s `onLocationSelect` and to `useMapModelContextTools`' `onLocationSelect`, so a human picking a search result and an agent calling `search-map-location` fly the map the same way and hit the same `SEARCH_COVERAGE_BOUNDS` check. All UI copy in `packages/web` (not the domain-agnostic SDK packages, whose own chrome — `SettingsMenu`, `ThemeToggle`, `BasemapToggle` — stays hardcoded English by design, since they can't depend on an app-specific message catalogue) is sourced from `@inlang/paraglide-js` messages in `messages/{locale}.json` (`en`/`af` — English, Afrikaans), compiled into the checked-in `src/paraglide/` (`messages:compile`, mirrored by `vite.config.ts`'s `paraglideVitePlugin`). `strategy: ["cookie", "preferredLanguage", "baseLocale"]` means a first-time visitor is served in their browser's `Accept-Language`, falling back to English, and a manual pick from `LanguageToggle` (web-local, wraps `@karta/map`'s generic `SegmentedControl`, rendered via `SettingsMenu`'s `children` slot) persists in a first-party locale cookie (`PARAGLIDE_LOCALE`, per `PRIVACY.md`) so SSR reflects it on the next request too — `entry.server.tsx`'s `handleRequest` wraps the render in `paraglideMiddleware` for exactly this (not `workers/app.ts`, see above), and `root.tsx`'s `Layout` reads `getLocale()`/`getTextDirection()` for `<html lang>`/`dir` rather than a fixed `"en"`. No `"url"` strategy: this app has one route, so locale-prefixed paths would add redirect/routing machinery with nothing to disambiguate.

- **Deploy** — Cloudflare Workers runs the wrapper entry (`packages/web/workers/app.ts`) which imports the built React Router server bundle (`packages/web/build/server/index.js`), and serves built client assets from `packages/web/build/client` (`wrangler.jsonc`). Two custom domains are routed to the same worker: `karta.timothybrits.co.za` (current, `SITE_URL`) and `buffer-zones.timothybrits.co.za` (the pre-rename hostname, kept alive purely so old links/bookmarks 301-redirect to the current one — see the `packages/web` entry above). `wrangler.e2e.jsonc` is a copy of `wrangler.jsonc` with that `routes` block removed, used only by the Playwright e2e preview server (see Commands above) so the suite never exercises the redirect. Full/100 Lighthouse scores and mobile-friendliness are a hard requirement, not aspirational — this drives decisions like the `.display.v1.geojson` simplification step (tuned to the largest tolerance that still leaves every township recognisable — see `MINIMUM_TRIANGLE_WEIGHT`/`GEOJSON_COORDINATE_PRECISION` in `data-pipeline`), deferring the choropleth fetch behind `MapView`'s `onReady`, and self-hosted variable fonts. `packages/web/public/_headers` sets a strict `Content-Security-Policy` with **no** `'unsafe-inline'` on `script-src` or `style-src` — the theme-bootstrap `<script>` is allowed only via its exact `sha256-` hash (see `root.tsx` above), and `style-src 'self'` works only because vanilla-extract emits static stylesheets, never inline styles. `img-src`/`connect-src` explicitly allowlist each basemap tile host (`tile.openstreetmap.org`, `server.arcgisonline.com`) and `nominatim.openstreetmap.org` for search/reverse-geocoding: registering a new basemap (`@karta/map`'s `registerBasemap`) or geocoder provider works fine against `npm run dev` (no CSP is applied locally) but is silently blocked by the browser in production until its origin is added here — this is the concrete case the `packages/map` entry above's "a host wiring up any provider is responsible for allowlisting its origin" note is about. `/data/*` gets a `stale-while-revalidate` cache header (1hr fresh, 24hr stale-while-revalidating) rather than `immutable`, since region GeoJSON is re-published in place by re-running the data pipeline rather than under a content-hashed filename.

## Conventions

- **TDD.** Write the failing test before implementation code, for both bug fixes and new features — the test is part of the change, not a follow-up, and a change without one is incomplete.
- **SOLID.** *Open/closed* is the load-bearing one here: this is an SDK, so new domains, regions, and transit sources get added by writing config — `DomainConfig`, `RegionPipelineConfig`/`PipelineSource`, the `REGIONS`/`METROS` registries (see Architecture above for where each lives) — never by branching on an id inside `@karta/core`/`map`/`react`. *Dependency inversion* is why that works: those SDK packages depend only on the abstractions they define (`DomainConfig`, `Layer`), never on `packages/app`'s or `packages/web`'s concrete data. This isn't just a review convention: `.dependency-cruiser.cjs` (run via `npm run depcruise`, wired into `npm run lint` and therefore CI) mechanically forbids `packages/core`, `packages/react`, and `packages/theme` from importing anything outside themselves, `packages/map` from importing `packages/app`/`packages/web`, and `packages/app` from importing `packages/map`/`packages/react`/`packages/theme`/`packages/web` — so a layering inversion fails `npm run lint` before it reaches review. The rest follow the same instinct at smaller scale: one module keeps one reason to change (*single responsibility*), a `Layer`/`LayerGroup` implementation must work anywhere the contract is consumed with no id-based special-casing (*Liskov substitution*), and hook/component props stay narrow and domain-agnostic — e.g. `MapView`'s `bounds`/`renderFeaturePopup` — rather than a catch-all options object (*interface segregation*).
- **DRY.** Shared logic belongs in `packages/core`/`map`/`react`, not duplicated per-app; a value hand-typed in more than one place (a font size, a colour, a duration) is a missing token, not a coincidence.
- **KISS / YAGNI.** Prefer the simplest design that satisfies current requirements; don't build UI, abstractions, or config surface for a second domain/region/consumer that doesn't exist yet — extensibility here comes from the config shapes above being open to it, not from pre-building the thing that would use them.
- **JSDoc on every exported function, const, type, interface, class, and component** (TSDoc-compatible: `@param`, `@returns`, `@remarks`, `@example`) — across every package, not just the SDK ones (`@karta/core`/`map`/`react`). Document the *why*/non-obvious behaviour, not just a restatement of the name; skip fields that are already self-evident from their name and type.
- **No code comments** unless they capture a genuinely non-obvious *why* (a constraint, a workaround, an invariant) — never restate what the code already says.
- **Expanded `if` statements with braces**, never single-line/braceless conditionals. Biome's `useBlockStatements: error` rule enforces this — don't disable it.
- **Accessibility is a priority**, not an afterthought — semantic HTML, keyboard navigation, focus states, and contrast should be considered in every UI change, in step with the Lighthouse-100 bar above.
- **British English spelling and grammar** in all user-facing copy (UI text, labels, error messages) — not in code identifiers.
- Prioritise **superpowers** skills for their intended workflows (brainstorming before creative/design work, TDD, systematic debugging, etc.) rather than working ad hoc.

## Delegating to sub-agents

Model tiers for any delegated work — both `Agent` tool calls and `agent()` calls inside a Workflow script. Set the `model` parameter explicitly on every call; never omit it, since omission silently inherits the session's model.

| Tier | Use for |
| --- | --- |
| `haiku` | Mechanical bulk work: renames, boilerplate, format conversion, log triage |
| `sonnet` | Default for well-specified implementation with clear acceptance criteria |
| `opus` | Genuinely tricky work: concurrency, subtle algorithms, adversarial verify/judge panels, gnarly debugging |

**Never use `fable` sub-agents, under any circumstance — not even with my approval.** Stick to the three tiers above; when unsure between them, pick the cheaper one and escalate on failure.

## Dynamic workflows (Workflow tool)

Applies to all sessions, on any model. Dynamic workflows are a normal tool here, not something to avoid — reach for the Workflow tool when a task has 3+ independent, parallelisable subtasks, or would benefit from a pipeline/judge panel.

Opt-in rule: if `ultracode` isn't already on for the session (no `ultracode` keyword, toggle, or an explicit orchestration request), propose the workflow in one or two sentences — its rough shape and cost — and wait for my go-ahead before invoking it. If `ultracode` is on, invoke directly.

Every `agent()` call inside a workflow script must set `model` explicitly, chosen from the tiers in "Delegating to sub-agents" above. `fable` is never valid there either — a Fable review, if genuinely warranted, runs after the workflow finishes as its own standalone `Agent` call (ask first, per above), never as a workflow stage.

## Design system

Karta adopts Google's Material 3 (M3) directly rather than an app-owned system: `--md-sys-color-*` role tokens (`primary`, `surface`, `surfaceContainer` → `surfaceContainerHighest`, `error`, etc., defined in `packages/web/src/index.css` with separate light/dark-mode values) are generated from a single brand seed colour via Material Color Utilities' HCT tonal-palette algorithm (`packages/web/scripts/generateM3Theme.ts`, `npm run generate:theme --workspace @karta/web` — never hand-edit the hex values inside the `/* GENERATED M3 ... TOKENS */` markers, the next run overwrites them). `--md-sys-shape-corner-*` and `--md-sys-elevation-shadow-1/2/3` follow M3's own baseline shape scale and elevation formula rather than app-chosen values. Every component is Karta's own plain React, styled with vanilla-extract (`*.css.ts`, colocated per component) against these tokens, not `@material/web` (Google's Shadow DOM custom element library) — that was tried and reverted: it required a client-only-mount gate per component to avoid crashing this app's Cloudflare Workers SSR (`ReferenceError: HTMLElement is not defined` under workerd) and a React hydration mismatch that came with it, plus unit tests that couldn't use `getByRole` at all since happy-dom never renders Shadow DOM. None of that friction is specific to Material 3 as a design system, only to that one library's delivery mechanism, so plain React gets the same HCT-generated colours/shape/elevation with none of it — see `docs/design-system.md`'s "Component library" section for the full rationale. `@karta/theme`'s `vars`/`mapLabelVars` (built with vanilla-extract's `createGlobalThemeContract`) give `.css.ts` files typed, compile-time-checked access to these tokens — declaring no values and emitting no CSS, so `index.css` stays the single source of truth for value generation and light/dark switching exactly as described above; see `docs/design-system.md`'s "Styling implementation" section. `@vanilla-extract/css` is consequently a real runtime `dependencies` entry of `@karta/map`/`@karta/theme`/`@karta/web` (they ship source with no build step), so any host embedding `@karta/map` must register `@vanilla-extract/vite-plugin`'s `vanillaExtractPlugin()` in its own Vite config. Karta keeps its own fonts — Inter Variable and Martian Mono Variable — throughout. Hover/pressed/selected states use the `--state-hover`/`--state-pressed`/`--state-selected` opacity-tint tokens, matching M3's own ripple/state-layer opacities. See `docs/design-system.md` for the full token reference. Keep new UI consistent with this rather than introducing ad hoc styles, fonts, or a second parallel design system.
